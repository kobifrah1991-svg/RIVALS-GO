# PROJECT_PLAN.md — Multiplayer Arena Shooter (Unreal Engine)

> מסמך עבודה ל-Claude Code. המטרה: לפתח בהדרגה משחק יריות עצמאי בהשראת קצב המשחק של RIVALS, בלי להעתיק קוד, מפות, דמויות או נכסים מוגנים.
> בעל הפרויקט אינו מתכנת. פעל באופן אוטונומי ככל האפשר, אבל אל תטען שפעולה בוצעה בלי אימות. אין לבצע רכישות, לפרוס שירותים בתשלום או לפרסם משחק בלי אישור מפורש.

## 1. תפקידך
אתה Claude Code, מהנדס Unreal Engine בכיר, מפתח רשתות, DevOps ובודק איכות. עבוד ישירות על הפרויקט הקיים במחשב. קודם בצע בדיקת מצב (audit), ורק אחר כך שינויים. העדף לשמר קבצים, Blueprints, מודלים וסקינים קיימים.

**חשוב:** אין להניח שיש לך שליטה ישירה בעורך Unreal או בשרת ענן. השתמש בכלים הזמינים בפועל. אם פעולה דורשת פתיחת GUI, התחברות לחשבון, אישור Firewall או תשלום — עצור, הצג למשתמש הוראה קצרה ומדויקת, ואז המשך.

## 2. טכנולוגיה ומגבלות
- מנוע יעד: Unreal Engine, בגרסה המותקנת בפרויקט. אל תשדרג ללא אישור.
- קוד: C++ יחד עם Blueprints לפי הצורך; Gameplay Framework, Enhanced Input, Replication.
- נכסים: השתמש בסקינים, דמויות וכלי נשק שכבר קיימים בפרויקט ובתיקיות שהמשתמש יבחר. בדוק רישיון ושימוש מסחרי לכל נכס שהורד מ-Fab / Marketplace; אין להניח שכל נכס מותר לשימוש בכל הקשר.
- תקציב: ברירת מחדל אפס עלויות. פיתוח ובדיקות רשת מקומיות תחילה. אין הבטחה לאירוח ציבורי חינמי וקבוע.
- פלטפורמת יעד ראשונית: Windows PC; התאמה לפלטפורמות אחרות רק לאחר MVP.
- ניהול גרסאות: Git, קובץ `.gitignore` מתאים ל-Unreal, README והוראות בנייה. אין להעלות סודות, מפתחות או קבצים גדולים שלא נדרשים.
- פרטיות ואבטחה: אימות בצד שרת, הרשאות אדמין בצד שרת, רישום פעולות; אין לשמור סיסמאות בקוד.

4. כתוב `PROJECT_STATUS.md`: מה כבר קיים, מה חסר, בעיות בנייה, וסיכוני תאימות.
5. צור `TASKS.md` עם משימות קטנות, תיבות סימון וקריטריוני קבלה.
6. בצע משימה אחת בכל פעם; לאחריה הרץ בדיקות/בנייה כשאפשר, תעד תוצאה אמיתית, תקן תקלות, והמשך.
7. אל תמציא תוצאות בדיקה. ציין במפורש מה נבדק בפועל ומה דורש בדיקה ידנית.

9. אל תתקין תוספים, תשנה הגדרות מערכת או תפתח פורטים ללא אישור.
10. שמור על משחק רץ גם בין שלבי הפיתוח; אל תבנה את כל המערכות בבת אחת.

## 4. אבני דרך לפי סדר

### שלב A — משחק בסיסי לשחקן יחיד
- דמות בגוף ראשון או שלישי, לפי הקיים; תנועה, ריצה, קפיצה, כיוון וירי.
- 3 נשקים לדוגמה: רובה, אקדח, נשק קרוב (לפי הנכסים הזמינים).
- מערכת חיים, נזק, תחמושת, טעינה מחדש, מוות ו-Respawn.
- מפה אחת, נקודות Spawn בטוחות, ממשק HUD: חיים, תחמושת וניקוד.
- שילוב נכסים קיימים ובדיקת אנימציות, collision ו-performance.

**קריטריון קבלה:** אפשר לפתוח מפה, לשחק, לפגוע במטרה, למות ולהופיע מחדש ללא שגיאות קריטיות.

### שלב B — Multiplayer תקין
- השתמש במודל **שרת סמכותי (server-authoritative)**: השרת קובע פגיעות, נזק, תחמושת, מוות וניקוד.
- Replication לתנועה, מצב נשק, ירי, חיים, אנימציות ותוצאות משחק.
- RPC עם בדיקות קצב ותקינות; הלקוח שולח בקשות, לא קובע לעצמו נזק/כסף.
- תחילה בדיקת Listen Server עם שני לקוחות ב-PIE/מחשבים מקומיים.
- אחר כך Dedicated Server אם גרסת המנוע, סביבת הבנייה ותצורת הפרויקט תומכות בכך.
- Lobby בסיסי: Host/Join, רשימת שחקנים, בחירת קבוצה, Ready, תחילת משחק.
- מצבי משחק ראשוניים: 1v1 ובהמשך 2v2; הרחבה ל-5v5 רק לאחר בדיקות עומס.
- טיפול בניתוק שחקן, יציאה באמצע משחק, Timeout וניסיון התחברות חוזרת.
- בדיקות latency, packet loss וסנכרון מצב.

**קריטריון קבלה:** שני לקוחות נפרדים נכנסים לאותו משחק, רואים זה את זה, יורים, מקבלים תוצאות עקביות והשרת מכריע.

### שלב C — חיבור לשרת
1. **מקומי, חינם:** הרץ שרת ולקוחות על המחשב או ברשת הביתית. כתוב סקריפטים להפעלה ותיעוד כתובות/פורטים.
2. **בדיקת אינטרנט:** הצע אפשרויות כגון חיבור ישיר, פתרון Relay/Session או שירות ייעודי; בדוק מגבלות NAT, Firewall, CGNAT, אבטחה ותנאי השירות. אל תפתח פורטים ללא אישור.
3. **אירוח ציבורי:** הצג טבלת חלופות לפי מחיר אמיתי, מגבלות, זמינות ותמיכה ב-Unreal Dedicated Server. אל תבטיח חינם לצמיתות.
4. הפרד בין **Game Server** בזמן אמת לבין **Backend** לחשבונות, מלאי, מטבע ונתונים מתמשכים.
5. שמור קונפיגורציית שרת בסביבה/קבצי הגדרות, לא בקוד; הוסף health checks, לוגים, גיבויים והוראות פריסה/עצירה.

**קריטריון קבלה:** תועד והודגם חיבור שני מחשבים בפועל; פריסה לאינטרנט רק לאחר אישור בעל הפרויקט.

### שלב D — מערכת אדמין מאובטחת
צור תפקידי `Player`, `Moderator`, `Admin`, `Owner`. **רק השרת** בודק הרשאות, לעולם לא UI בלבד.

פקודות אדמין מבוקשות:
- `/heal <player> [amount]` — ריפוי שחקן.
- `/giveweapon <player> <weapon_id>` — הענקת נשק מאושר.
- `/givemoney <player> <amount>` — הענקת מטבע משחק בלבד.
- `/sethealth <player> <amount>` — שינוי חיים בגבולות מוגדרים.
- `/kick <player> [reason]` — הוצאת שחקן.
- `/ban <player> [duration] [reason]` — חסימה עם תיעוד.
- `/announce <message>` — הודעת שרת.
- `/teleport <player> <destination>` — רק אם נדרש, עם בדיקות תקינות.

ממשק אדמין בתוך המשחק: רשימת שחקנים, חיפוש, בחירת פעולה, אישור פעולות רגישות, משוב הצלחה/כישלון. לוג Audit עם מזהה אדמין, שחקן יעד, פעולה, ערך, זמן ותוצאה. הגבלת קצב וגבולות סכומים. אין להעניק הרשאות לפי שם שחקן בלבד; השתמש בזהות מאומתת בצד שרת. פקודות כסף ונשקים חייבות לעבור דרך שירות המלאי/כלכלה המרכזי כדי למנוע כפילויות.

**קריטריון קבלה:** שחקן רגיל אינו יכול להפעיל פקודות אדמין אפילו באמצעות בקשות רשת מזויפות; פעולות מורשות נרשמות.

### שלב E — כלכלה, סקינים וחנות
- XP, רמות, מטבע וירטואלי, מלאי ופתיחת פריטים.
- חנות ראשונית **ללא כסף אמיתי**: סקינים, קוסמטיקה, שדרוגים מאוזנים.
- תכנון מזהים יציבים לפריטים, מחירים, עסקאות אטומיות ומניעת רכישה כפולה.
- נתונים מתמשכים בצד Backend/DB עם אימות הרשאות. אין לסמוך על יתרת כסף בצד לקוח.
- תכנון רכישות בכסף אמיתי לעתיד בלבד; לא לממש סליקה לפני החלטה על פלטפורמה, גילאי יעד, מדיניות החזרים, רגולציה ותשלומים.

**קריטריון קבלה:** מטבע, מלאי ורכישות נשמרים בין כניסות; לא ניתן להעניק לעצמך כסף באמצעות שינוי מקומי.

### שלב F — איכות, אבטחה והפצה
- בדיקות משחק, בדיקות Multiplayer, מקרי קצה, בדיקות עומס בסיסיות.
- מדידת FPS, זמני טעינה, רוחב פס ושימוש בזיכרון.
- מסך הגדרות, אודיו, רגישות עכבר, נגישות בסיסית.
- Build ל-Windows, חבילת בדיקה, README למשתמש והוראות שרת.
- רק לאחר אישור: פרסום גרסה ציבורית.

## 11. חזון מסחרי, השקה וצמיחה
המטרה ארוכת הטווח היא משחק עצמאי מצליח למחשב, עם אפשרות להפצה ב-Steam ובהמשך בחנויות מובייל. הצלחה מסחרית או באז תקשורתי אינם מובטחים; יש למדוד עניין אמיתי מצד שחקנים.

### תכנון פלטפורמות
- **PC קודם:** בניית גרסת Windows יציבה, משחקיות ממכרת, שרתים, מערכת חשבונות ובדיקות.
- **Steam בהמשך:** הכנה לתהליך Steamworks, דף חנות, נכסי שיווק, בדיקות build, הישגים/חברים לפי הצורך, מדיניות פרטיות ותנאי שימוש. אין לפתוח חשבון, לשלם דמי הצטרפות או לפרסם ללא אישור.
- **מובייל לאחר אימות:** בחינת התאמת Unreal, ביצועים, ממשק מגע, UI רספונסיבי, בקרות, משקל התקנה, דרישות Android/iOS, חנויות ותנאי הפצה. אין להבטיח שהמשחק למחשב יעבוד בטלפון ללא התאמות.
- **Cross-play רק לאחר בדיקת היתכנות:** תכנון זהות משתמשים, גרסאות תואמות, שרתים, בקרות, איזון ומשחק הוגן בין פלטפורמות.

### מיתוג ושיווק
- צור שם משחק מקורי וזכיר, לוגו ושפה חזותית מקוריים, לאחר בדיקת זמינות וסיכוני סימני מסחר.
- בנה תהליך Demo/Playtest סגור, אסוף משוב ונתוני שימור משתמשים בהסכמה ובכפוף לדין.
- הכן בהמשך טריילר קצר ממשחקיות אמיתית, צילומי מסך, ערכת עיתונות, דף נחיתה וערוצי קהילה.
- מדוד: יציבות, מספר שחקנים פעילים, שיעור חזרה למשחק, זמן למציאת משחק, חוות דעת וביקוש לרשימת משאלות.
- הימנע מהבטחות שיווקיות לא מבוססות ומקניית עוקבים/ביקורות.

### שפות ברמת שרת וממשק
- **השרת אינו 'בשפה אחת':** נתוני משחק ופקודות נשלחים כמזהים/קודים ניטרליים לשפה. כל לקוח מציג אותם בשפת המשתמש.
- רשימת השרתים, שמות מצבי משחק, הודעות מערכת, הודעות ניתוק, התראות אדמין, לובי, ניקוד, חנות ותוצאות — כולם מתורגמים לפי בחירת כל שחקן בנפרד.
- שני שחקנים באותו שרת יכולים לראות את אותו אירוע, האחד בעברית והשני ברוסית או בערבית.
- טקסט חופשי של שחקנים (שמות חדרים/צ'אט) לא מתורגם אוטומטית. הוסף בעתיד סינון ודיווח, ואם יתבקש — תרגום אופציונלי עם גילוי נאות.
- שמור בחירת שפה בפרופיל או מקומית, ולא בהגדרת שרת משותפת.

### החלטות מסחריות שנשארות לאישור בעל הפרויקט
מודל תמחור (משחק בתשלום/חינמי), מדיניות מיקרו-תשלומים, פלטפורמות השקה, תאריך השקה, הוצאות שרתים ושיווק. אין להפעיל תשלומים או לפרסם ללא אישור.
